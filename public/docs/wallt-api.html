Overview

The Wallt API is a read-only enrichment layer. You send it raw text from any external service — a message body, a scanned PDF excerpt, a sensor reading — and it tells you which of Atlantist's six BIM sectors are relevant, and how strongly.

It is stateless and ephemeral. No request data is stored. No messages are retained. The API is purely a routing and scoring engine — it directs your payload through sector-specific pre-filters and returns a relevance-weighted response with a request_id for traceability.

No data retention

Wallt API never stores or logs your request payloads. Audit logs contain only sector routing decisions and status codes, never message content.

Authentication

The Wallt API uses a single Bearer token passed in the Authorization header. Tokens are issued by the Atlantist team — contact api@atlantist.cloud to request one.

Header format

Authorization: Bearer WALLT_API_TOKEN_xxxx

Token acquisition

Getting a token

Tokens are issued manually by the Atlantist team. Provide your service name, expected request volume, and intended use case. No self-serve portal yet — email api@atlantist.cloud.

Endpoints

POST /api/wallt-api/ingest

Accept an external service payload and return a sector-enriched response. The only required field is text — the raw input string you want Wallt to analyze.

Request body

FieldTypeRequiredDescription
text string Yes Raw input text, message body, prompt, or extracted content. Max 10,000 characters. Excess is silently truncated.
context object No Context object. Accepts project_id (string) and user_id (string) for future routing. Currently informational only.

Minimal request example

{
  "text": "The W12×40 beam spans 24 ft with a uniform load of 2.4 kip/ft. Check for L/240 deflection and AISC section compliance. Also flag any NFPA 13 sprinkler clearance conflicts."
}

Full request example (with context)

{
  "text": "Structural bay 4B has a 6in CMU load-bearing wall with a 4ft opening for a fire-rated door. Verify header size per NYC BC Table 2308.6.1 and check NFPA 13 sprinkler head clearance within 18in of the opening.",
  "context": {
    "project_id": "proj_nyc_brooklyn_resi_2026",
    "user_id": "usr_engineer_perez"
  }
}

Handling 429

When you receive a 429, respect the Retry-After header. Do not retry immediately — implement exponential backoff (e.g., wait Retry-After seconds, then double on subsequent failures, cap at 5 minutes).

Integration Examples

WhatsApp scanner (Node.js)

Monitor messages via liber-whatsapp-monitor or your own WhatsApp webhook. Forward message text to Wallt for sector enrichment.

const response = await fetch('https://nexaxis.polsia.app/api/wallt-api/ingest', {
  method: 'POST',
  headers: {
    'Authorization': 'Bearer WALLT_API_TOKEN_xxxx',
    'Content-Type': 'application/json'
  },
  body: JSON.stringify({
    text: messageBody, // WhatsApp message text
    context: {
      project_id: 'liber-whatsapp',
      user_id: messageFrom
    }
  })
});

const data = await response.json();
if (data.sector_count > 0) {
  console.log(`Wallt flagged ${data.sector_count} sector(s): ${Object.keys(data.sectors).join(', ')}`);
  console.log(`Request ID: ${data.request_id}`);
  if (data.soft_links) console.log(`Cross-link: ${data.soft_links}`);
}

Email monitor (Python)

Poll an IMAP inbox or receive webhooks from your email provider. Forward subject + body to Wallt for sector routing.

import requests

response = requests.post(

    }

data = response.json()
print(f"Sectors: {list(data['sectors'].keys())}")

# Log request_id for debugging / support

Relevance scoring

Each sector assigns a relevance score (0.0 – 1.0) based on keyword matching against its trigger list. A score above 0 means the sector is active. Higher scores indicate stronger thematic match.

Formula: relevance = min(hit_count / total_triggers + 0.1, 1.0)

Multiple hits of the same keyword count once. Case-insensitive matching. Scores are rounded to two decimal places in the response.

Cross-sector soft links

When two or more sectors are active on the same request, Wallt generates a soft_links string that names the cross-domain relationship:

"soft_links": "Cross-sector analysis: Structural × Fire Protection"

This signals that the payload touches areas where structural loads and fire egress requirements may interact — useful for flagging multi-disciplinary review needs.

Error Handling

Wallt API uses standard HTTP status codes. All error responses are JSON with error and code fields.

HTTPCodeDescriptionAction
400 BAD_REQUEST Request body is missing or the text field is empty / not a string. Fix the request body and retry.
401 UNAUTHORIZED Missing or malformed Authorization: Bearer header. Add a valid Bearer token.
403 FORBIDDEN Token value does not match the configured WALLT_API_TOKEN. Verify your token with the Atlantist team.
422 UNPROCESSABLE Request body is structurally valid JSON but fails validation (e.g., text exceeds 10,000 characters). Truncate text to 10,000 chars and retry.
429 RATE_LIMIT_EXCEEDED More than 100 requests in the current 1-hour window. retry_after field shows seconds until reset. Wait retry_after seconds, implement backoff.
500 INTERNAL_ERROR Unexpected server error. Include request_id in your support email. Retry after 30s. Contact api@atlantist.cloud with the request_id.
504 TIMEOUT Request exceeded the 10-second processing limit. Partial results may be returned with timeout: true flag. Retry with a shorter text payload.

Partial results on timeout

When a 504 occurs, Wallt may return whatever sectors resolved before the timeout — subject to server state. Always check for a timeout: true flag in the response body.

{
  "ok": false,
  "error": "Request timed out after 10s",
  "code": "TIMEOUT",
  "timeout": true,
  "partial_sectors": {
    "structural": { "relevance": 0.72, "status": "available" }
  },
  "request_id": "wtapi-1748529600000-a7x2k9"
}

Security

Read-only guarantee

Wallt API is a pure enrichment engine. It accepts a text payload, scores it against sector filters, and returns the result. No data is written to any database. There is no POST to a persistent store, no conversation log, no message archive.

No message content in audit logs

Server-side audit logs record only:

  • HTTP status code and response size
  • Sector routing decisions (which sectors fired)
  • request_id and timestamp
  • Rate limit state

Audit logs do not include your text payload or context object. The token identifies the caller but not the content of the request.

CORS policy

Wallt API does not enforce browser CORS — it is intended for server-to-server calls from your backend services. If you need to call it from a browser, you must proxy through your own server. Direct browser calls are unsupported.

Token hygiene

  • Never embed the token in client-side JavaScript or public repositories.
  • Store it in environment variables or a secrets manager (Vault, AWS Secrets Manager, etc.).
  • Rotate tokens by contacting api@atlantist.cloud.
  • If a token is compromised, request immediate rotation — old token is invalidated within 5 minutes.
